# The login that could never succeed (2026-09-07)

## Symptom

Signing in showed **"Those details did not match — double-check your college ID
and password"**, with the browser console blaming `erpFetchAttendance`. The
credentials were correct. No OTP screen ever appeared.

## What was actually happening

`/api/erp-login` has a trusted-device fast path: if the college returns a full
session, skip the OTP screen. It decided "full session" by checking for
`sessionId` and `apiKey`:

```js
if (result.session && result.session.sessionId && result.session.apiKey) { … }
```

The real login response, captured live in
`proxyman/cuiet.codebrigade.in_07-20-2026-19-56-14.har`, is:

```json
{ "status": "4",
  "mobileString": "email address gur****@chitkara.edu.in",
  "data": [{ "userId": "24635", "sessionId": "20", "apiKey": "A001vt20260720070653", … }] }
```

**Status 4 means "we just emailed an OTP" — and it carries `sessionId` and
`apiKey` anyway.** The one field it does not carry is `token`, the server-issued
`securityToken` that every `mobilev2` call validates; only `/mobilev2/verifyOtp`
issues that.

So the fast path fired on *every* login. The app skipped the OTP screen, minted
a session with an empty `securityToken`, and immediately called
`/api/erp-attendance`. The college rejected it, `checkSessionAlive` confirmed
dead twice, and — because onboarding did not pass along the sign-in it had just
been handed — the server took the harshest branch and answered a bare
`401 {error: 'Session expired'}`. `friendlyError` saw a 401 during sign-in and
told the student their password was wrong.

Every part of that chain was doing what it was told. The premise was wrong.

Introduced in `38ebbbb` (2026-08-18). It has blocked every new sign-in since.
Students already connected before that date were unaffected — their tokens are
real.

Why the tests missed it: `silent-refresh.test.js` asserted the status-4 case
with an invented fixture, `data: [{ userId, roleId }]` — no `sessionId`, no
`apiKey`. The fixture, not the code, was what passed.

## The fix

`reloginERP` is now the only place that decides trusted-vs-OTP, and it requires
the thing that actually makes a session work:

```js
if (login.status !== '4' && s && s.sessionId && s.apiKey && s.securityToken) {
```

- `api/_erp-provider.js` — `loginLegacy` passes the college's own `status` through.
- `api/_session-utils.js` — the single decision, above.
- `api/erp-login.js`, `api/erp-session.js` — stop re-deriving "trusted" from
  `sessionId + apiKey`; `reloginERP` has already decided. The duplication was
  the bug: `requestOtp` had its own copy, so "Sign in again" would have reported
  success while an OTP sat unread in the student's inbox.
- `api/erp-session.js` (`check`) — a stored session with no `securityToken` is
  now reported invalid, so the junk tokens this bug handed out retire themselves
  at launch instead of failing every sync forever.
- `src/utils/friendlyError.js` — a `sessionExpired` or `revoked` answer no longer
  reads as a rejected password. That mislabel is what made a session bug look
  like a credentials bug.
- `ERPSetupScreen` / `ERPConnectScreen` — the first attendance call now carries
  the `persistentToken` it was just given, so a genuine hiccup during onboarding
  gets the reconnect answer rather than "no stored sign-in at all".

## Verification

`api/__tests__/login-otp-required.test.js` drives `/api/erp-login` with the
**verbatim captured** status-4 body and asserts it answers `needsOtp` with no
token; `silent-refresh.test.js`'s status-4 fixture now carries `sessionId` and
`apiKey` too, so the old shortcut can never pass again.

Full chain replayed against the captured payloads (login → verifyOtp →
register):

```
1. LOGIN      200 {"needsOtp":true,"gotToken":false}
2. VERIFY OTP 200 {"gotToken":true,"gotPersistent":true,"name":"…"}
3. ATTENDANCE 200 1 subjects: Data Structures using OOP-II 73/89
   college calls: appLoginAuthV2 → verifyOtp → showAttendance → getAttendanceRegister
```

On the committed baseline the same replay gives `{"trusted":true,"gotToken":true}`
at step 1 and never reaches the college again — the before/after of the bug.

Suite: 34 suites / 265 passed / 1 skipped. `bash build.sh` green. Onboarding
walked end-to-end in the browser against `vercel dev` to the Today screen.

## Known, not fixed

`npx jest --runInBand` fails `adminAnalytics` and `security-hardening` through
cross-suite interference. It fails the same way on the committed baseline; the
default (parallel) run is green. Test hygiene, not product behaviour.
