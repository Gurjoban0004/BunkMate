## C — Critical

### C1. The ERP's OTP second factor is effectively disabled for every Presence user

`api/_session-utils.js` → `generateDeviceUUID`:

```js
crypto.createHash('md5').update(`presence-device-${username}`).digest('hex')
```

The "device" identity the ERP trusts is an **unsalted MD5 of the roll number**. Roll numbers are
public and sequential (`2410990296`). So:

- Anyone can compute any student's `deviceIdUUID` offline, with no access to anything.
- The ERP's trusted-device exemption is keyed on it, so once a student has completed OTP **once**,
  anyone holding their password can log in from any machine **with no OTP at all** — the
  `trusted` branch in `api/erp-login.js` hands back a full session.
- It is not per-device, it is per-username. "Trusted device" means "trusted username", forever,
  everywhere. Reinstalling, changing phones, or a different browser makes no difference.

This converts the university's MFA into single-factor auth for exactly the population that
installs this app.

**Fix direction.** Mint a random UUID per install, persist it in `AsyncStorage`, and send it from
the client. Real devices then get real trust and a new device correctly requires OTP. If a
server-derived value must be kept short-term, at minimum HMAC it with `ENCRYPTION_SECRET` so it is
not externally computable — but that is a mitigation, not the fix; it is still one identity per
username.

**Consequence to accept:** the fix means students will see OTP on each new device. That is the
correct behaviour and should not be designed around.

### C2. The 4-digit OTP can be brute-forced

`/api/erp-verify-otp` has no rate limiting, no attempt counter and no lockout. The OTP is four
digits (`docs/HANDOFF-erp-mobile.md`, and the client only checks `length < 4`). That is 10,000
possibilities, ~5,000 requests on average, against an endpoint that answers as fast as the ERP
does. The `authUserId` ticket is valid for 15 minutes, which is ample.

Combined with C1 the picture is worse: an attacker who knows a roll number can trigger an OTP
(`/api/erp-login` is also unauthenticated) and then brute-force it.

**Fix direction.** Per-ticket attempt counter — 5 tries then the ticket is dead. The Firestore
limiter in `auth-token.js` (`allowAttempt`) is the existing pattern to copy; key it on the ticket
rather than the IP so it cannot be sidestepped by rotating IPs.

### C3. `/api/push-send` is callable by anyone on the internet

```js
const secret = process.env.CRON_SECRET;
if (secret && req.headers.authorization !== `Bearer ${secret}`) return res.status(401)...
```

`CRON_SECRET` is **not set in any environment** — verified with `vercel env ls`. With no secret the
guard is skipped entirely, so an unauthenticated `GET`/`POST` sends a push notification to every
subscribed user and runs an unbounded `collectionGroup('push')` read. Repeatable at will.

The payload is server-controlled, so this is spam and quota burn rather than content injection —
but it can also get the VAPID keys throttled by the push services, which breaks reminders for
everyone.

**Fix direction.** Invert the guard so a missing secret fails closed:
`if (!secret || req.headers.authorization !== ...) return 401`. Then set `CRON_SECRET` in Vercel.
Failing closed matters more than the env var: the same shape will recur elsewhere.

### C4. Unauthenticated credential proxy with no rate limiting

`/api/erp-login` takes a username and password from anyone and replays them to the university
portal. No rate limit, no captcha, no backoff. This is a credential-stuffing oracle **pointed at
the university**, hosted on your infrastructure and attributable to you. Two concrete risks beyond
the obvious: the university blocking Vercel's egress IPs, which breaks the app for every user;
and students' ERP accounts being locked out by attempts they never made.

This matters more now than it did last week — you are about to hand this URL to ~50 people.

## H — High

### H1. `/api/auth-token` is dead in production

Full write-up in **`docs/BUG-auth-token-esm.md`**. Firebase custom-token sign-in is down, so cloud
sync and every client Firestore operation fail. Deferred by the user on purpose; not blocking the
research collection drive.

### H2. The reminder-time control does nothing for almost everyone — two independent bugs

**Bug one.** `vercel.json` schedules `push-send` as `30 12 * * *` — once daily, 12:30 UTC = 18:00
IST. The handler then filters subscriptions to those whose `reminderTime` starts with the *current*
IST hour. So only users on `18:xx` are ever matched. Any student who sets 09:00 gets nothing,
silently, forever. The handler's own docstring claims it is "scheduled hourly", which is what the
code was written against; the cron says otherwise.

Fix either way, but pick deliberately: make the cron hourly (`0 * * * *`) and keep the filter, or
keep the daily cron and drop the per-hour filter and the setting with it. Shipping a time picker
that is honoured for one value is worse than not shipping one.

**Bug two.** `src/utils/webPush.js` exports `updateWebPushTime`, and **nothing anywhere calls it** —
verified by grep across `src/`. `SettingsScreen` only calls `enableWebPush` on the toggle. So
changing the reminder time updates local state and never reaches the server, even for the one hour
that would have worked.

### H3. `admin-analytics` reads entire collections on every open

Seven unbounded reads (`api/admin-analytics.js`):

- L80/L82 `collectionGroup('syncs')` — L82 is the no-filter fallback, the whole collection
- L94/L294/L327 `collection('users').get()`
- L95/L139 `collectionGroup('semesters').get()`

Only L268 has a `.limit(200)`. `telemetry/{userId}/syncs` grows one document per sync per user with
no TTL — there is already a `ponytail:` comment in `src/services/telemetry.js` admitting this. With
50 students syncing through a semester this becomes tens of thousands of documents, read in full
every time the admin panel opens, against a 15s function limit.

It will not fail loudly. It will get slower, cost more, and then start timing out.

**Fix direction.** Bound every query, and add a TTL policy on `telemetry/*/syncs`. The admin panel
does not need raw history — it needs aggregates.

### H4. Installed APKs hard-depend on a Vercel alias that can move

`src/services/apiConfig.js` falls back to `DEFAULT_NATIVE_API_BASE =
'https://presence-gurjobanpanjeta.vercel.app'`, and **no EAS build profile sets
`EXPO_PUBLIC_API_BASE_URL`** — all three profiles in `eas.json` have `env: {}`. So every APK bakes
in that hostname at build time.

If the project is renamed, the alias is reassigned, or the deployment is moved, **every installed
APK breaks permanently** and the only remedy is a new build and a re-install by every user. The
PWA has no such problem: it calls `/api/*` same-origin.

This is a plausible contributor to the "APK login is shady" history, alongside the fact that an APK
cannot be hot-fixed the way the service worker updates the PWA.

**Fix direction.** Put a stable custom domain in front of the API and set
`EXPO_PUBLIC_API_BASE_URL` explicitly per profile. A domain you control is the only thing that
makes a shipped APK survivable.

## M — Medium

### M1. `/api/admin` has no rate limiting

Authorisation is sound — the roll number is read from the AES-GCM-sealed session token, never from
the body (this was fixed previously and is correct). But there is no limiter on the endpoint, so
it is a free oracle for testing stolen session tokens against.

### M2. Admin write actions are not audited

`updateConfig`, `publishAnnouncement`, `revokeUser` and `unrevokeUser` mutate global state with no
record of who did what, when. With one admin that is survivable; the moment there are two, or a
token leaks, there is no way to reconstruct what happened. `revokeUser` in particular cuts off a
real student's access.

### M3. Session tokens never expire

`encryptSession` / `encryptPersistent` are documented as having no expiry, and
`decodeSessionRollNumber` performs no time check. A leaked token is valid forever, including an
admin one. There is a revocation list, but it is keyed on roll number and checked only on some
paths.

### M4. The client's OTP timeout is longer than the server's

`API_TIMEOUT` is 20s in `src/services/erpService.js`; `vercel.json` caps functions at
`maxDuration: 15`. The ordering is correct — the client outlives the server — but the margin is
5 seconds for a login that makes several ERP round-trips on a mobile network. A slow ERP produces a
Vercel 504 with an HTML body, which surfaces as `NON_JSON_RESPONSE`. That path *is* handled and
maps to "Your university portal is not responding", so this is a plausibility note rather than a
confirmed defect — worth checking against real logs during the drive.

## F — Fixed during this audit

### F1. A rejected login logged nothing at all

`api/erp-login.js` returned 401 on `ERP_REJECTED` without logging anything, discarding the ERP's
own message and the response shape. This is the single reason the live login bug below took so long
to pin down: five real 401s in production with **no trace of why**.

Now logs `[LOGIN-REJECTED]` with the payload's keys, `status`, `error`, `message` and whether an
`authUserId` was present. It never logs the username or password — there is a test asserting that.

### F2. `assertNotLoginFailure` rejected logins the ERP had accepted

`api/_erp-provider.js` treated **any truthy `payload.error`** as a credential failure. Several ERP
responses carry `error` as a present-but-empty value; `'0'` and `'false'` are both truthy strings in
JS. An MFA challenge (`status: 4`) carrying such a field was reported to the student as "Those
details did not match. Double-check your university ID and password."

Now only an `error` with real content counts, and `status` 0/error/fail still rejects. 14 tests
cover the accept and reject cases, including `''`, `'0'`, `false` and `null`.

## The live login bug (open — needs one retry to close)

**Symptom.** A new student enters her ID and password, receives the OTP, and is never logged in.
Error shown: *"Those details did not match. Double-check your university ID and password."* She
changed her university password twice trying to fix it.

**What is established, from production logs:**

- Five `POST /api/erp-login → 401` at 19:59, 20:03, 20:07 (×3).
- **Zero `POST /api/erp-verify-otp` calls in the same window.**

So she never reaches the OTP screen. It fails at login. That matches the error text exactly:
`handleLogin` in `ERPSetupScreen.js` passes `friendlyError(err, 'signin')`, whose 401 branch is
that message. The OTP step would have said "That code did not work".

**The paradox that identifies the bug:** the ERP *sent her the OTP*, which means it accepted her
credentials and issued a `status: 4` challenge. Our own code then rejected that challenge. The only
path returning 401 from `erp-login` is `err.code === 'ERP_REJECTED'`, thrown by
`assertNotLoginFailure` — which is precisely the over-eager check fixed in F2.

**F2 is therefore the leading candidate and may already be the fix.** It is not confirmed, because
the exact payload her account returns has never been seen. F1 now captures it.

**To close this:** deploy, have her try once, then read the ERP's actual response:

```bash
vercel logs https://presence-blue.vercel.app --json 2>/dev/null \
  | python3 -c "
import sys, json
for line in sys.stdin:
    line = line.strip()
    if not line.startswith('{'): continue
    try: d = json.loads(line)
    except: continue
    m = str(d.get('message') or '')
    if 'LOGIN-REJECTED' in m: print(m)
"
```

If she logs in, F2 was it. If she does not, `[LOGIN-REJECTED]` names the field that is wrong, and
the fix is one condition in `assertNotLoginFailure`.

**Do not** ask her to change her university password again. Nothing observed points at her
credentials, and each change risks locking her account.

## What is actually in good shape

Worth stating so a later session does not "fix" it:

- **Admin authorisation.** The roll number comes from the sealed session token, never the request
  body. `admin.js` and `admin-analytics.js` both do this correctly.
- **Admin config controls are load-bearing.** All six writable keys — `maintenanceMode`,
  `maintenanceMessage`, `minVersion`, `updateUrl`, `autoSync`, `calendarSync` — are read by the
  client. Verified per key. `updateConfig` also whitelists keys and flags, and rejects unknown ones
  rather than writing a control that silently does nothing.
- **The OTP ticket binding.** Sealing `authUserId` to its username at login closed a real
  privilege escalation and the design is right.
- **PWA update path.** The service worker is network-first with `skipWaiting()`, so an online user
  always gets fresh code. This is why the OTP contract change shipped safely.
- **Research pipeline.** Verified end to end on real data; the dataset build refuses to write a CSV
  whose totals disagree with the portal's own.

## On "keys baked into the APK" — verified, and why fetching them at runtime is not the fix

Raised 2026-09-06: the concern that anyone with an APK extractor can pull our keys, and the
proposed remedy of serving keys from an endpoint the app fetches at startup.

**What is actually in the shipped bundle** (checked against the live 2.4MB bundle):

| Absent ✓ | Present |
|---|---|
| `ENCRYPTION_SECRET` | Firebase web config (`AIzaSy…`, authDomain, projectId) |
| `FIREBASE_SERVICE_ACCOUNT` / any `BEGIN PRIVATE KEY` | VAPID **public** key |
| `VAPID_PRIVATE_KEY` | API base URL (`presence-gurjobanpanjeta.vercel.app`) |
| `CRON_SECRET` | Admin roll number `2410990296` |
| `ERP_SCHOOL_CODE`, `ERP_BASE_URL`, any university host | |

**No credential that grants anything is in the app.** That is not luck — it is the existing
architecture working. The Vercel functions *are* the backend: ERP credentials are posted to them,
encrypted server-side with `ENCRYPTION_SECRET`, and only opaque tokens come back. The university's
own endpoint is not even visible to the client.

**The Firebase `apiKey` is not a secret.** It is a project identifier for API routing, documented
as public by Google, and it appears in every web Firebase app ever shipped. It authorises nothing.
Access is decided by Firestore rules (`research/**` denies all clients; `users/{id}` requires
`request.auth.uid == id`) and by server-side checks. Treating it as a leak leads to hiding the
wrong thing.

**Why fetching keys from an endpoint does not help.** If the app can fetch a value at runtime with
no secret, so can anyone — they call the same endpoint with `curl`. Protecting *that* endpoint
requires a credential in the app, which is the original problem. **Anything a client can obtain, an
attacker can obtain.** The scheme adds a network round-trip, a startup failure mode, and an
offline-launch bug, in exchange for obscurity that a proxy defeats in one request. Do not build it.

**What does help, in order:**

1. **Firebase App Check** — attests that requests come from your genuine app build, which is the
   real answer to "someone extracted our config and is calling our project". This is the thing
   worth doing.
2. **API key restrictions** in the Google Cloud console — restrict the key to the Android package
   name + signing certificate, and to the specific APIs it needs.
3. **C1–C4 above.** The extractable value that actually costs something is not in the bundle at
   all: it is `generateDeviceUUID`, which anyone can compute from a roll number without opening an
   APK at all.

**Minor, related.** `src/services/adminService.js` gates the Admin tab on
`ADMIN_ROLLS.includes(roll) || roll.startsWith('admin')`. The server has no `startsWith` rule, so a
spoofed roll reveals an admin UI whose every call 403s — cosmetic, and the code says so. It does
disclose which roll number is the admin, which is a hint worth removing when C1 is addressed.
